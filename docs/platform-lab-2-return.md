## The timer result changes the pacing design

Every combination of libc nanosleep, direct kernel clock_nanosleep, timeout-only
poll and timerfd, requesting1/2/5ms, idle/loaded and50us/1ns slack, gives cell
means9.844–10.003ms. Maximum11.629ms; no failed samples. Timer slack is restored
exactly to50000ns. Kernel clock_getres and all timer-list bases report10000000ns.

The timer list identifies `arch_sys_counter` and `arch_sys_timer`, with a stated
15001ns clock-event minimum. Fine timestamp/event hardware does not prove that
this kernel is running high-resolution user waits. The behavior is consistent
with low-resolution timer operation; CONFIG_HIGH_RES_TIMERS/CONFIG_HZ values are
not recovered because `/proc/config.gz` is absent. Both probed tracefs paths and
clk_summary are unavailable. Do not turn path absence into a kernel-wide claim.

An intended1ms pacing/backoff sleep is therefore an expensive wall-time gate.
Changing libc to direct syscall or timerfd did not fix it. Reducing slack did not
fix it. Avoid a broad busy-spin replacement; audio readiness can wake earlier.
